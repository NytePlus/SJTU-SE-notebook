### MemCached

#### Memcached - principle

- 首次访问：从RDBMS（关系型数据库）中取得数据保存在memcached
- 第二次访问：从memcached中取得数据显示页面
- 本质上其实每次访问都是先访问memcached，如果能找到就直接返回，否则进入RDBMS
- 如果对数据做修改：
  - 先对memcached做修改再落盘
- 但是这种频繁写的数据完全没有必要进入memcached
  - 所以book中的库存数量就没有必要进入memcached
  - 此时应该把stock解耦出去，变成一张单独的表

#### redis过期逻辑与问题处理：

问题1：雪崩

每过一段时间（比如3600s，一个小时），就会认为redis中的数据全部失效

- 此时大量访问书的请求无法命中
- 这种**同时的全部失效称为雪崩**
- 解决方法：将一千本书分为10个100本，将失效时间错开

问题2：击穿

- 依然可能存在的问题：如果同时有大量请求对同一本书进行，此时redis中没有被存储，此时**所有请求会同时进入数据库（这种情况称为击穿）**，但是全部只要一个数据，导致这一次大量请求涌入根本没有用到redis
  - 解决方法：所有请求都在访问同一本书时，加一把锁，在书被取回到redis后，再放开锁（也就是有一个请求拿到了书后），剩下的请求全部从缓存中获取
- 另一种击穿情况：大量请求同时查询一本不存在的书（因为此时一定会进入数据库进行查询）
  - 可以添加一个布隆过滤器来很大避免这种情况的出现



**在集群部署方案中，使用了 Redis 缓存来存储 HttpSession 对象，请问，即使不使用 Redis，HttpSessior对象也会存储在内存中，那么为什么要使用 Redis 来存储 HttpSession 对象呢?**

1. 服务器重启session不易丢失
2. 便于集群session维护，所有服务器都到redis服务器拿session
3. 便于水平方向扩展，多个redis

#### **全文搜索的核心步骤**

1. **分词处理**
   将文本按照词语或关键词进行拆分，生成分词结果。
2. **建立索引**
   对分词结果进行存储和排序，方便后续的快速查询。
3. **查询匹配**
   根据用户输入的查询条件，在索引中查找匹配的文本内容。

**使用场景**

- 适用于文本量较大的场景，如电子书、博客、社交媒体、邮件等。
- 企业内容管理系统（CMS）。
- 搜索引擎（如 Elasticsearch、Solr 等）。



#### Lucene

**Lucene** 是一个高性能、全功能的文本搜索引擎库，提供了构建全文搜索引擎的基础工具。

- 它是一个 Java 库，主要用于处理底层的索引与搜索。

对**非结构化数据**建立索引，搜索索引

- **正向索引：按照文档顺序存储文档内容及其对应的元信息。**即每个文档的哪行包含了什么；

  - 特点：
    - 检索时需要逐个扫描文档，效率较低。
    - 易于记录文档的完整信息。
  - 正向索引**适用于需要按文档检索的应用**，例如文档管理系统或内容展示；
  - 正向索引**需要更多的存储空间**，但在访问特定文档时速度较快；

- 高效交叉索引：某一个关键词出现在 哪个文件 哪个位置 （反向索引

  ![1736668331059](assets/1736668331059.jpg)

  - 上图为一个反向索引的例子，记录了关键词在文档中出现的次数等信息

- **反向索引：将关键词与文档的对应关系存储起来，方便通过关键词快速定位文档。**

  - 反向索引适用于需要全文搜索和关键词检索的应用，例如搜索引擎和信息检索系统。
  - 反向索引占用较少的存储空间，**在全文搜索和关键词检索时速度更快。**

#### Core Indexing Classes

- 建立索引：
  - 读文档； **Analyzer** 是文本分析的关键组件； 用于分词、去除停用词、提取关键词等。
    - 常用的 Analyzer：
      - `StandardAnalyzer`：标准分析器，适用于大多数场景。
      - `WhitespaceAnalyzer`：仅按空格分词。
      - `KeywordAnalyzer`：不分词，直接使用整个输入作为一个关键词。
    - 自定义分析器：可以根据需求定义分词规则和停用词表。
  - **IndexWriter**：用于创建和维护索引。
    - 功能：添加文档到索引、更新索引、删除文档、优化索引等。
    - 索引存储：Lucene 使用 **`Directory` 抽象类**来管理索引的存储（可以是文件系统、内存等）
  - **Document 表示索引中的一个文档**，**文档通常由一组字段（ Field ）组成**；**域Field 是文档中的一个字段或属性。它包含了字段的名称、值以及用于指定如何处理该字段的 配置选项**（关键词域keywordField不参与索引；LongField；TextField tokenizer断开）
- 搜索
  - parse解析
  - 可以指定在某个域里找

#### 索引文件标准格式

- 核心概念包括：index, document, field and term.
- An index contains a sequence of documents. 一个索引由很多个文档组成
  - document 表示一个索引中的文档，包含多个 field。
  - Field 表示文档的一个属性，如标题、正文、作者等，由很多个term组成
  - A term is a sequence of bytes. 项，也就是具体的词

index：documents：field：terms(项，具体的词)

- fields具备的可选属性：
  - **存储（Stored）**：是否将字段值存储在索引中。
  - **索引（Indexed）**：是否将字段内容索引以供搜索。
- segments：索引很长 分段

#### 搜索

Lucene 支持多种查询方式，如简单关键词查询、布尔查询、范围查询等。

- 通过优化的反向索引结构和自定义的打分机制，Lucene 能够高效地提供相关性排序结果

具体的搜索实现：

- 多个 `TermQuery` 实例组合起来，可以构建更复杂的查询；多个 `BooleanClause`，每个子查询都有一个运算符（来自 `BooleanClause.Occur`），该运算符描述子查询如何与其他子查询组合。

  - **SHOULD**：子查询可以出现在结果集中，但不是必须的。如果所有子查询都是 `SHOULD`，则结果集中的每个文档至少匹配一个子查询。
  - **MUST**：子查询必须出现在结果集中，并且会影响评分。结果集中的每个文档将匹配所有这样的子查询。
  - **FILTER**：子查询必须出现在结果集中，但不影响评分。结果集中的每个文档将匹配所有这样的子查询。
  - **MUST NOT**：子查询不能出现在结果集中。结果集中没有文档会匹配这样的子查询。

- **打分机制：可以自定义**

  - 为了获得更高的得分，尽量增加查询词在重要字段（如标题）中的频率，并使用稀有且相关的关键词，同时保持字段内容简洁以提高权重。

  ![1736669735629](assets/1736669735629.jpg)

  | **因素**                     | **描述**                                                     |
  | ---------------------------- | ------------------------------------------------------------ |
  | **tf(t in d)**               | 术语 (**t**) 在文档 (**d**) 中的词频因子。表示该术语在文档中出现的频率。 |
  | **idf(t)**                   | 术语的逆文档频率。表示该术语在整个文档集合中的稀有程度，稀有的术语对得分影响更大。 |
  | **boost(t.field in d)**      | 字段提升因子，通常在索引时设置，用于提升特定字段的权重。     |
  | **lengthNorm(t.field in d)** | 字段的长度归一化值，根据字段中的词语数量进行归一化。此值在索引时计算，并存储在索引中。 |
  | **coord(q, d)**              | 协调因子，基于文档中匹配查询项的数量来计算。匹配的查询项越多，得分越高。 |
  | **queryNorm(q)**             | 查询的归一化值，根据查询项的加权平方和计算。确保查询项更多的查询不会不公平地影响得分。 |
